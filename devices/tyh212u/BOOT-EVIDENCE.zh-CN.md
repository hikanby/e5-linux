# TYH212U 原厂启动器与实验内核入口

2026-11-14。本文记录已核对的启动器代码及离线入口方案。
尚未进行替换内核启动，也没有可刷入的 boot.img 或 OpenWrt 固件。
脱敏数值见 [boot-stock-evidence.json](boot-stock-evidence.json)。

## 原厂包与现装启动器

机主提供的 PAC 为 `TYH11.0.0.10Q`、`ums9620_2h10`。其 BOOT 与既有原厂
`boot_b` 备份的全部 64 MiB 逐字节一致。PAC 的 XML 只提供板级名称，
不能单独唯一确认手机型号。

经机主明确授权，通过现有 ADB/root 只读核对 `uboot_a` 和 `uboot_b`。
两个分区均为 3 MiB，主机和手机分别计算的 SHA-256 均与 PAC 的
UBOOTLoader 完全一致。这使包中启动器代码与现装二进制建立了对应关系。
本次没有写入手机、重启或改变槽位；原始负载与采集记录只保存在机主本地。

## 已闭合的 Android 交接路径

UBOOT 的 AArch64 代码从文件偏移 `0x200` 开始。以下偏移均相对此处，
用于定位代码；推导的链接基址 `0xb5000000` 不等于已测得的运行地址。

Android caller 在 `0x220f0` 经 wrapper `0x21f5c` 调用 loader `0x213a0`。
loader 的原始及 gzip 内核路径均将目标设为 `0x80080000`。成功返回后，
caller 在 `0x22124/0x22128` 以 `x0=0xbbf00000` 转入交接函数 `0x1f260`。
其最后几条指令把 `x1/x2/x3` 清零，设置 `x4=0x80080000`，在 `0x1f328`
执行 `blr x4`。最后交接没有读取新 Image 的偏移来重算入口。

同一二进制还有 generic bootm 路径，不能把它的入口调整逻辑直接套在上述
Android caller 链上。部分清理 helper 的间接效果尚未穷尽，本次也没有观察
手机实际执行的分支、CPU 入口状态或最终地址上的内存内容。

DTB 段也有独立处理：Android DT table 会选择内层裸 FDT，再进行
`sprd,sc-id` 匹配、保留内存修正、条件 overlay 和全局 fixup。
部分条件路径可以修改目标指针，最终 caller 仍传固定的 `0xbbf00000`；
实际运行所走分支与最终 FDT 内容还需核对。不能把原始 DT table 容器直接传给内核，
也不能把内嵌静态 FDT 等同于已运行 Android 的 live DT。

## 可借鉴的入口包装

固定 Linux 6.18 的 Image 头中 `text_offset=0`，原厂内核为 `0x80000`。
固定提交 `020b970e351eee3887e6caaf2d653926e7086e44` 的
`Documentation/arch/arm64/booting.rst` 要求实际 Image 起点为
2 MiB 对齐基址加 `text_offset`。
所以直接把新 Image 放在 `0x80080000` 不满足其放置条件。

原项目的 `upstream/wrap-image.py` 提供了可评估的办法：在完整原生 Image 前
增加 `0x180000` 字节的入口与填充，使原生 Image 落在 `0x80200000`。
外层第一条指令 `0x14060000` 是直接分支 `b +0x180000`，保留 DTB 参数 x0
和其他寄存器，不进行运行时内存复制。原生 Image 的头与代码全部保持原样。
外层头的 `text_offset` 为 `0x80000`，有效大小为填充加原生 `image_size`。
这与只修改原生 Image 的头字段有不同的实际内存布局。

最新已核验 Image 来自 Actions `43492110439`，适配提交
`15deb048e4a34f0c97c5520491d7d972225f381c`：

| 项目 | 字节数或区间 |
| --- | --- |
| 原生文件大小 | 6,467,592 |
| 原生有效内存大小 | `0x670000` = 6,750,208 |
| 包装后的候选文件大小 | 8,040,456 |
| 包装后的候选有效内存大小 | `0x7f0000` = 8,323,072 |
| 原生 Image 候选有效范围 | `[0x80200000, 0x80870000)` |
| 包装整体候选有效范围 | `[0x80080000, 0x80870000)` |

整个有效范围与已知 live DT 保留项没有重叠。文件末尾以外的 282,616 字节
仍属于内核所需内存，不能只按文件长度检查。区间算术不能验证启动器临时分配、
DMA、缓存、实际装载长度或最终 DTB；此方案仍属于离线准备。

## 离线检查工具

`tools/image_entry.py` 是本机型的独立检查入口。默认只输出计划：

```sh
python3 devices/tyh212u/tools/image_entry.py inspect /absolute/path/to/Image
```

工具只接受本次产物使用的零偏移、小端 4 KiB、flags `0xa`、无 PE/COFF 的
NOP+B 入口格式，并检查原生分支目标、完整有效大小和选定 DT 空隙的几何边界。
它不鉴定输入内核来源。复用 Image 前仍应核对对应构建提交、配套模块及摘要。

显式 `wrap` 子命令可写入一个新的入口组件及清单，拒绝覆盖文件和重复包装。
在 Linux 构建环境使用此写入操作时，应通过 `tools/build-release.py` 的
`run --command-only` 记录日志并获取工作区锁。`verify --source` 可以只读核对包装头、
填充、分支目标和原生负载逐字节一致。输出清单明确标记 DTB、AVB、CPU 状态、
启动器临时内存和硬件测试均未验证。

12 项针对性测试覆盖分支实际解码、头字段、完整内存大小、原生负载保持、
未知入口拒绝、异常长度、越界、重复包装和文件保护。最新真实 Image 已在内存中
通过 `inspect`；本轮没有生成真实入口组件或 boot 镜像。

## 现有 Magisk A 与原厂 B 的 AVB

另外只读分析了既有 A/B 启动备份。两份内嵌 vbmeta 的内部摘要和 RSA 签名均有效，
其 boot 公钥相同，并与顶层 vbmeta 的 boot chain 公钥对应；这只是元数据内部
数学验签与链中 key 对应，没有核实手机平台的受信根。

原厂 B 的 payload 摘要与 descriptor 匹配；现有 Magisk A 的不匹配。
A/B descriptor 的 image_size 均为 33,351,680，A 的实际 payload_end 已为
33,671,168。A/B 的内嵌元数据及内核段也分别存在字节差异，不能将其直接解释为
Magisk 原样保留了 B 的元数据，也没有把内核差异归因于 Magisk。

因此，有原厂 AVB 元数据不是永久无法适配的充分证据；现有备份也不能证明新
Linux 内核会被接受。`boot_v2.py` 对含 AVB 元数据的负载修改拒绝保持有效，
后续需要有明确接受条件的独立 adapter，不能直接绕过检查或伪造签名。

## 首次启动仍需补齐

需要专用最小 RAM 配置及板级 DT、可读回的日志、明确的 boot/AVB 接受条件和
可核对的恢复步骤。当前平台编译配置内置 UFS、PMIC 等组件，不挂载分区也可能
探测硬件。入口包装本身不提供这些条件，不会生成 Android boot 容器或完成签名。

完整 OpenWrt 的 USB、供电、蜂窝和 Wi-Fi 等支持仍需各自适配与实机验证。
